bezier-trajectory · repo orientation

One Rust solver, one Python door, four kinds of caller

A Bézier-curve SCvx trajectory optimizer. The numerics live in Rust; everything Python-side is a shell around it. The layout only makes sense once you see that every caller reaches the solver through a single file.

01The shape of it

02The solver — Rust

All the mathematics. optimizer.rs is the one that matters: it holds the SCvx loop, the penalized merit, the ρ ratio test, the trust region and every stopping criterion. The rest are supporting kernels it calls.

ModuleHoldsTouch it when
optimizer.rsSCvx loop, merit + ρ, trust region, stop reasons, exact Gram objectiveConvergence, acceptance, termination
constraints.rsKOZ supporting half-spaces (exact + self-consistent rows), boundary-condition rowsKeep-out geometry, Prop 1 certificate
de_casteljau.rsSegment subdivision matricesHow the curve is split for the KOZ
bezier.rsDerivative (D), elevation (E) and Bernstein Gram matricesCurve algebra in control-point space
gravity.rsTwo-body + J2 acceleration and its JacobianPhysics model
pybind/src/lib.rsPyO3 wrapper → the bezier_opt wheelAdding or removing a solver parameter

Rebuilding matters. Editing Rust does nothing until the wheel is rebuilt and force-reinstalled — maturin develop does not work here. Bump CACHE_VERSION in orbital_docking/cache.py too, or you will silently read stale results.

03The Python library

orbital_docking/ is the door plus its furniture. Two modules are a separate concern: they consume the solver's answer as a warm start for a downstream collocation solver rather than optimizing anything themselves.

FileRole
optimization.pyThe gateway. Only importer of the wheel; owns caching, BC assembly, reported metrics, the parallel sweepcore
cache.pyDisk cache keyed by a hash of every solver argument. CACHE_VERSION lives here
constants.pyEarth μ, radius, J2, KOZ radius, TRANSFER_TIME_S = 1500
bezier.py · de_casteljau.py · constraints.pyNumPy twins of the Rust kernels — used by tests and tools as an independent checkoracle
visualization.pyAll plotting and the interactive HTML output
j2_validation.pyValidates the J2 model against reference data
downstream_collocation.pyTurns a solved curve into a warm start for direct collocationdownstream
dymos_t6.pyDymos/OpenMDAO cross-check built on that warm start. Optional heavy dependencydownstream

04Three independent test layers

They are genuinely independent — different languages, different oracles, different failure modes. The Rust suite cannot see a Python regression and the pillars cannot see a Rust unit bug.

LayerWhereCountWhat it would catch
Rust unit + goldencore/src/*.rs, core/tests/baseline_test.rs24Gram integral wrong, KOZ rows not exact at the reference, solver stopping for no stated reason
Python suitetests/{unit,integration,property,regression}86Kernel drift between NumPy and Rust, KOZ violated end-to-end, golden run moved
Verification pillarstools/verify/6Convergence, optimality and conservatism claims — the numbers that go in the paper

Run order: cargo test -p bezier_opt_core, then pytest, then the pillars. The pillars are slow and call the real solver many times.

05The verification pillars

Each writes artifacts/verify/<pillar>/summary.md ending in a VERDICT line; verdict.py greps those and aggregates. They share one scenario grid and one true-objective oracle in harness_common.py — the single most load-bearing file in the harness.

ScriptAsks
1nlp_crosscheck.pyDoes an independent, solver-blind SciPy NLP reach the same optimum?
2ablation.pyWhich change was actually the fix? (trust region vs proximal)
3kkt_check.pyIs the returned trajectory primal-feasible on a dense grid?
4adiagnostics.pyPer-iteration health: ρ, trust, slack — and is the returned iterate the best one visited?
4bsweep.pyDoes it hold across the N × n_seg × scenario grid?
5optimality.pyIs it actually optimal? External KKT residual + a search for any improving feasible direction

Scenario grid: phase70, phase120, phase135, phase170, planechange. Larger phase lag means the keep-out sphere binds harder. phase170 is nearly antipodal and needs its own larger trust radius, which is why r0 is a per-scenario field.

One genuine exception. tools/spacetime_optimize.py is a separate solver, not a frontend. It reuses only the Bézier and De Casteljau matrices, then runs its own SCP over (x, y, t) for moving obstacles. It does not touch the Rust core.

07Where the authority lives

  • doc/design_freeze.md — read this first. §0 is the exact problem formulation, §9 the KOZ decision, §5 every parameter with the principle that picked it, §7 the evidence log. It outranks the paper.
  • CLAUDE.md — the terse rules; the objective is singular and hard-coded, and Δv is never mentioned in the paper.
  • doc/paper_draft_korean_rev2.md — currently lags the code and is being rewritten toward it. Never edit code to match the paper.
  • artifacts/verify/ — pillar output. Gitignored, so it carries no provenance; regenerate before quoting any number.
